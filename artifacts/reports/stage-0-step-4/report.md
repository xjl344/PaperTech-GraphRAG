## 为什么需要冻结

步骤 3 的选材脚本会覆盖工作清单。后续解析、检索和评测需要知道自己使用的是哪一批论文，因此本步骤将工作清单及其依据复制到独立版本目录：版本号说明使用哪批材料，SHA-256 用于检查内容是否改变。

`freeze-pilot.py` 不覆盖已有版本；复查已有版本使用 `--verify-only`，需要调整试点时应审查差异后另建版本。验证命令不会修改快照。快照没有设置操作系统只读权限；若文件被外部修改，校验会报错。

## 快照内容

| 文件 | 用途 |
|---|---|
| `pilot-manifest.json` | 正式清单，包含版本、时间、14 篇路径/哈希、用途、选择理由、引句定位及来源映射 |
| `pilot-manifest.csv` | 便于人工查阅的论文与哈希表 |
| `excluded-files.json` | 本轮未入选的 249 个 PDF 路径和哈希；仅表示未纳入本轮主题预检，不表示失败 |
| `inputs/` | 当时的工作清单、选材说明、环境版本、步骤 2 盘点基线及预检/冻结脚本快照 |
| `evidence/previews/` | 当时的 14 篇逐页文本预览，使选材引句可脱离可变的步骤 3 文件核对 |
| `checksums.json` | 其余 29 个快照文件的 SHA-256，用于检测缺失、多出或内容变动 |

PDF 保留在只读使用的 `database`，本步没有复制、移动或改写源 PDF。验证源文件仍需要本地语料目录存在。问题示例与引句仅是选材证据，不是正式答案金标，也不是阶段 1 的稳定 Chunk。

## 验证与失败行为

发布前先核对 14 篇源文件与步骤 2 基线一致、理由非空、预检通过、引句的页号及字符范围匹配，再在临时目录完成写入并重查源哈希，最后重命名为版本目录。异常时不发布成功版本；临时目录可保留供排查。运行时发现已有同名版本会拒绝覆盖。

独立复查核对了 29 个快照文件、14 篇当前源 PDF、14 处原文字符范围及语料指纹。另做 7 项行为验证，结果见 `verification-cases.json`：

1. 正常快照可以验证。
2. 不依赖仍在变化的步骤 3 工作清单。
3. 已有版本拒绝再次发布覆盖。
4. 在独立副本中改动输入文件，会被校验检出。
5. 模拟源 PDF 哈希变化，会被校验检出。
6. 非法版本路径会被拒绝。
7. 验证和被拒绝的发布不会改动已冻结快照。

篡改检查只修改 `.cache/temp` 中的独立测试副本，源哈希变化以函数替代方式模拟，未修改真实 PDF。测试副本保留用于排查。文件校验用于发现内容变化，不提供数字签名或外部身份认证。

本步通过 V02（14 篇试点范围）；执行环境为 Windows / Python 3.14.6，冻结脚本仅依赖标准库。所保存的 PDF 预检环境为 PyMuPDF 2.1。未使用模型、索引或评测集。没有失败问题编号，验证输出没有失败项。

## 运行方式与边界

现在只需复查，不要再次创建同名版本：

```powershell
.\.venv\Scripts\python.exe -X utf8 scripts\freeze-pilot.py --verify-only
```

首次冻结使用不带 `--verify-only` 的命令；`pilot-v1` 已存在，再运行会报 `FileExistsError`，这是避免覆盖的预期行为。未来经确认调整选材后，可用 `--version pilot-v2` 创建新版本，旧版本保留。
